# F2F Bank — E2E тестирование

> **Проект:** Автоматизированное E2E-тестирование банковского приложения  
> **Стек:** Python + pytest + Playwright  
> **Приложение:** [f2f_bank_tests](https://github.com/IrinaStyazhkina/f2f_bank_tests) — тестовое приложение для отработки ручного и автоматизированного тестирования  

---

## О проекте

Данный репозиторий содержит набор end-to-end тестов, покрывающих основные пользовательские сценарии банковского приложения: регистрацию, вход, переводы, пополнение баланса, историю транзакций и профиль.

Тесты написаны с использованием Python, pytest и Playwright. Архитектура тестов спроектирована так, чтобы каждый тест был независимым и мог выполняться параллельно.

## Запуск приложения

### Требования
- Docker
- docker-compose

```bash
# Перейти в папку с приложением и запустить
cd f2f-bank-tests
docker-compose up -d
# Приложение будет доступно на http://localhost
```

## Запуск тестов

```bash
# Перейти в папку с тестами
cd tests-py

# Установка зависимостей (один раз)
pip install -r requirements.txt

# Установка браузеров Playwright (один раз)
playwright install chromium

# Запуск всех тестов (параллельно, 4 воркера)
pytest

# Запуск конкретного файла
pytest tests/test_register.py

# Запуск конкретного теста по названию
pytest tests/test_login.py::test_tc08_login_with_valid_data

# Запуск в 1 поток (без параллельности)
pytest -n 1

# Просмотр отчёта
start report.html
```

## Архитектура тестов и подход к выполнению

### Параллельное выполнение тестов

Тесты спроектированы как независимые друг от друга и могут выполняться в параллельном режиме без влияния на состояние других сценариев.

Параллельность обеспечивается через `pytest-xdist`. Количество воркеров можно изменить под ресурсы окружения.

### Изоляция тестовых данных

Каждый тест генерирует собственные тестовые данные и не зависит от заранее подготовленных пользователей. Для этого в зависимости добавлен `faker`.

### Важное замечание по архитектуре данных

Несмотря на удобство текущего подхода, генерация пользователей напрямую через UI/API в каждом тесте может создавать избыточную нагрузку на базу данных. На практике чаще применяется мокирование, фикстуры и готовые тестовые данные.

### Браузерная валидация

В приложении реализована браузерная валидация, которую Playwright не может увидеть напрямую, так как она не находится в DOM. Для получения текста ошибки используется `evaluate`.

**Особенность:** сообщения могут отличаться в зависимости от настроек браузера и режима запуска (например, при запуске отдельных тестов ошибки показываются на русском, а при запуске всех тестов — на английском).

## Краткое описание найденных багов и неожиданного поведения

### Общие замечания

E2E-тестирование, как правило, фокусируется на критически важных пользовательских сценариях, поэтому такие тесты редко относятся к низкому приоритету из-за их стоимости поддержки и выполнения.

Тем не менее, в наборе тестов сознательно использованы сценарии с разными уровнями приоритета, чтобы продемонстрировать понимание принципов приоритизации.

Также следует отметить, что описанные ниже наблюдения не охватывают весь объём проведённого ручного тестирования.

---

### Общие проблемы приложения

#### Валидация и консистентность ввода

- Отсутствуют ограничения на максимальную длину input полей (кроме телефона на странице переводов).
- Поведение числовых полей не определено:
  - допускается ввод как точки (`.`), так и запятой (`,`), без явной спецификации.
- Сообщения об ошибках и подсказки интерфейса различаются по:
  - формулировкам
  - языку
  - стилю отображения
- При использовании подсказок input-поля теряют корректное визуальное оформление (фон становится белым).
- Поля Amount содержат Numeric Spinner.

---

### Страница логина

- Пароль может быть доступен в DevTools в elements.
- Поле email принимает кириллицу после `@`. Может быть `qwerty@привет.ru`. Строгой спецификации нет, в тесты не добавлял, необходимо уточнить документацию.
- При нажатии на иконку банка в хедере происходит попытка загрузить страницу переводов и отображается ошибка "Failed to load balance"

---

### Страница регистрации

- Пароль допускается длиной в 1 символ (отсутствуют минимальные требования к сложности).
- Поля Name и Surname могут принимать только пробелы.
- Поле email принимает кириллицу после `@`. Может быть `qwerty@привет.ru`. Строгой спецификации нет, в тесты не добавлял, необходимо уточнить документацию.
- При нажатии на иконку банка в хедере происходит попытка загрузить страницу переводов и отображается ошибка "Failed to load balance"

---

### Главная страница (Переводы)

- Отсутствует подтверждение операции перевода перед отправкой транзакции.
- Поле Phone:
  - допускает ввод произвольных символов после точки
  - допускает добавление символов после валидного номера
- Отсутствуют ограничения на максимальную длину полей ввода.
- Сервер возвращает HTTP 400 Bad Request при недостаточном балансе (возможно, более уместен 402 Payment Required).
- Денежные значения допускают неограниченное количество знаков после разделителя (ожидается ограничение до 2 знаков).

---

### Профиль

- Присутствует placeholder изображения профиля, однако отсутствует функциональность загрузки аватара.

---

### Транзакции / Пополнение баланса

- Низкий контраст текста и фона (светло-серый на белом), что ухудшает читаемость.
- При вводе некорректного значения в поле Amount отсутствует сообщение об ошибке.
- Отсутствует обратная связь пользователю при ошибочном вводе.
